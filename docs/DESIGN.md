# Fukugan 設計書

複数ウェブカメラで立体（3D）映像を撮影し、VR ヘッドセットで視聴できる形で
配信するシステム。第一原理で最小の核から設計する。

## 1. 最小の核

```
カメラ ×2 ─→ 同期 ─→ 左右合成 (side-by-side) ─→ 符号化 ─→ 配信 ─→ ヘッドセットで視聴
```

- 余分な部品を持たない。サーバーは「アプリ内蔵の簡易 HTTP 配信」だけでも
  完結し、外部の MediaMTX は任意の追加経路にすぎない。
- プロセスは 1 つ。スレッドは「カメラごとの読み取り」と
  「合成＋符号化」の 2 種だけ。
- 依存は OpenCV / NumPy のみ。符号化は FFmpeg をサブプロセスで使う
  （ライブラリとしてリンクしないので、環境ごとの FFmpeg をそのまま使える）。

## 2. モジュール構成

| モジュール | 役割 |
|---|---|
| `fukugan/config.py` | 設定の定義と検証。検証は「理由つきのエラー一覧」を返す |
| `fukugan/sources.py` | 入力源。実カメラ（OpenCV）と仮想カメラ（テストパターン生成） |
| `fukugan/sync.py` | 時刻でフレームを組にする同期ロジック（純粋関数として切り出し可能） |
| `fukugan/compose.py` | 左右合成、オフセット調整、平行化マップ適用 |
| `fukugan/calibrate.py` | チェッカーボードによる単眼・ステレオ較正、結果の保存/読込 |
| `fukugan/encoder.py` | FFmpeg コマンド構築、NVENC の実地プローブと自動フォールバック |
| `fukugan/pipeline.py` | 全体統括。状態機械と「理由つき」の状態公開 |
| `fukugan/server.py` | 内蔵 HTTP（UI / HLS / プレビュー / 制御 API） |
| `fukugan/webui/index.html` | 制御 UI（単一ファイル、日英切替） |
| `fukugan/cli.py` | 起動入口。設定ファイル読み込みとアプリ起動 |

## 3. 入力源の抽象

入力源は `read() -> (timestamp, frame) | None` と `name` を持つだけの
単純な契約にする。実カメラと仮想カメラはこの契約の背後で差し替え可能で、
パイプライン本体はどちらが来ているかを知らない。

仮想カメラは検証のために存在するが、製品の一部として同梱する
（実カメラのない環境でも全経路を試せることが、利用者の最初の成功体験になる）。

仮想カメラのフレームには以下を描く:

- 左右で視差を持たせた矩形群（合成結果を目視で確認できる）
- フレーム番号を 2 進バーコード帯として上部に描く
  （配信後のフレームから番号を機械的に読み戻し、「フレームが進んでいる」
  ことを自動検証できる）
- 経過時間テキストと動くマーカー

## 4. 同期

ソフトウェア同期の前提: USB カメラにハードウェア同期はない。
各カメラのフレームには「読み取り直後の単調時計の時刻」を打つ。

- 同期器は各入力の直近フレーム列から、基準時刻（最も新しいフレームの時刻）
  に最も近いフレーム同士を組にする。
- 組の時刻ばらつきが許容値（既定 50ms）を超えた入力については、
  直前のフレームを使い回し「劣化（degraded）」として数える。
  使い回しが上限（既定 5 回）を超えたら、その入力は停止扱いにし、
  状態に理由を明記する。
- 古すぎるフレームは捨てる。遅れた分を追いかけるためのキューは持たない
  （ライブ配信で遅延を積み上げるより、落として最新に追随する方が正しい）。

精度の限界は正直に書く: USB の転送遅延とドライバのバッファリングにより、
実効精度は数十 ms オーダーであり、速い動きでは左右のずれが見える。
これはソフトウェア同期の原理的な限界であり、隠さない。

## 5. 合成（side-by-side）

- 出力は 1 フレームに左右を横並びにした side-by-side 形式。
  Quest 3 のブラウザ/プレイヤーが標準で扱える、最も互換性の高い形式。
- 各眼は出力の半分の幅にリサイズする。既定は入力 1280×720 ×2 →
  出力 2560×720。
- 位置合わせは 2 段:
  1. 較正済みなら平行化（rectification）マップを適用する。
  2. 手動オフセット（眼ごとの x/y ピクセル移動）を常に適用できる。
     較正なしでも実用に足る調整手段を残すため。

## 6. 3 台以上の扱い

全台をステレオ化はしない。決めは次のとおり:

- **主ペアは「最も外側の 2 台」**（左端と右端）。基線が最大になり
  奥行き効果が最も得られる。
- **中央のカメラは同期の基準とフォールバック**に使う。
  - 同期の基準時刻は中央カメラのフレーム時刻を優先する
    （幾何の中心が時間の中心にもなる）。
  - 主ペアの片方が停止したら、中央カメラで代替し「劣化」を表示する。
- 設定で主ペアを明示指定することもできる（既定の自動選択を上書き）。
- 4 台以上でも同じ規則（最外ペア＋中央基準）。増えた台は
  フォールバック候補として保持するだけで、合成の複雑さは増やさない。

理由: 台数を増やす価値は「視点の多様化」ではなく「冗長性と基線長」に
あると割り切る。多視点合成は別の製品の仕事である。

## 7. 較正

- 2 台構成ではチェッカーボードによるステレオ較正を行う。
- 手順: 両カメラで盤面を同時に写した画像組を集める →
  `calibrateCamera` で各眼を較正 → `stereoCalibrate` →
  `stereoRectify` で平行化マップを生成。
- 結果は 1 つのディレクトリに保存する:
  - `calibration.json`（カメラ行列、歪み係数、回転・並進、再投影誤差などの数値）
  - `maps.npz`（平行化マップ。数値配列なので JSON ではなくこちら）
- 再起動時はこの保存結果を読み込んで再利用する。再投影誤差が閾値を
  超える較正は「質が低い」として警告つきで読み込む（黙って使わない）。

## 8. 符号化

- FFmpeg をサブプロセスとして起動し、標準入力に rawvideo (bgr24) を流す。
- ハードウェア符号化は「使える環境では使う」:
  - 起動時に NVENC で 1 フレームだけ実際に符号化してみる実地プローブを行う。
  - 成功すれば `h264_nvenc`、失敗すれば理由を記録して `libx264` に落ちる。
    「エンコーダ一覧に載っている」ことと「実際に動く」ことは別であり、
    一覧だけで判断しない（GPU のない環境では一覧にあっても失敗する）。
- 出力は 1 つの FFmpeg プロセスから複数出せる:
  - HLS（内蔵 HTTP が配るセグメント＋プレイリスト）
  - RTSP または SRT（利用者が指定した MediaMTX 等の URL へ push）

## 9. 配信と視聴

- 内蔵 HTTP 配信（既定）: `http://<端末のアドレス>:<ポート>/hls/index.m3u8`
  をヘッドセットのブラウザ/プレイヤーで開く。side-by-side 映像として
  再生設定すれば立体視できる。
- 外部 MediaMTX（任意）: RTSP/SRT で送れば、MediaMTX 側の
  HLS/WebRTC 変換で視聴できる。Fukugan は MediaMTX を同梱も起動もしない。
- プレビューは MJPEG で UI に出す（確認用であり、本配信とは別系統）。

## 10. 状態と失敗の扱い

「黙って失敗しない」を全モジュール共通の原則とする。

- パイプラインは状態機械を持つ: `idle / starting / running / degraded / error`。
- すべての失敗は理由文字列を伴い、`/api/status` と UI に表示される。
  例: 「カメラ 1 が開けません（デバイスが使用中の可能性）」、
  「NVENC の実地プローブに失敗したため libx264 を使用中」、
  「カメラ 0 の同期ずれが続いたため直前フレームで代替中」。
- カメラが 1 台も開けない場合は開始自体を拒否し、理由を表示する。

## 11. プライバシーと公開範囲

- テレメトリなし。外部送信は、利用者が指定した配信先への映像 push のみ。
- 内蔵 HTTP サーバーは既定で `127.0.0.1` にだけ bind する。
  ヘッドセットから見るには LAN 向けに bind する必要があるが、
  それは利用者が設定で明示した場合のみ。その場合も認証はないため、
  「同じ LAN の誰でも映像を見られる」ことを README と UI の両方で警告する。

## 12. 検証方針

- 単体テスト: 同期、合成、較正の計算、符号化コマンド構築、設定検証。
- 実走検証: 仮想カメラで キャプチャ→同期→合成→符号化→HLS→HTTP 取得
  までを通し、取得したフレームのバーコード帯からフレーム番号を読み、
  「番号が進んでいる」ことを確認する。
- 実カメラ・実 GPU・実ヘッドセットでの確認は、この開発環境では
  実施できないため未検証として README に明記する。
